# 模块图谱化业务规则 Prompt

根据用户给出的功能描述或模块名称，先建立 Graphify 图谱，再输出该模块的详细、可追溯业务规则和测试专项说明。

## 输入

- 项目根、源码范围、用户的功能描述/模块名/业务术语，以及已有需求、文档、图谱（如有）。
- 可选：模块输出路径、受众、LLM 语义提取授权、测试优先级或外部环境证据。

开始先写：已知事实、信息缺口、冲突、时效不明项、范围外和最小假设。术语无法精确映射时给出候选并标“待确认”，不要自行扩写需求。

## 你要做的事

1. 从需求词映射代码候选：路由/消息/任务、服务、领域实体、状态、Mapper/SQL、配置、外部客户端和测试。
2. 先构建或刷新覆盖该源码的 Graphify 图谱，执行模块词、候选符号和触发至下游的路径查询。
3. 复核最小完整链路的源码与查询定义，识别主流程、替代入口、异步任务、异常/回滚和外部边界。
4. 在项目本地生成一个专项 Markdown；同一模块所有主/支链路合并到同一章节，不后置重复模块。

## 执行规则

- 规则分为三层：资格过滤（能否进入候选）、候选排序（谁先处理）、运行时控制（限额、去重、并发、发送、失败回滚）。
- 对排序逐项写明字段、升降序、null/空值规则、并列行为、后置过滤和最终终止条件；以实际比较器或 SQL ORDER BY 为准。
- 关系图必须显示上游触发、模块决策、数据/缓存/日志与下游消费者；对状态实体补生命周期图。
- 图谱 INFERRED 边只能列为待核实线索；源码、SQL/XML、配置和运行证据分别标注。
- 测试点要可执行：数据前置、操作、可观察结果、来源/日志、优先级；外部系统用桩或明确未执行边界。

## 最低覆盖清单

- [ ] 模块定义、业务目标、角色、触发、输入、输出和依赖边界。
- [ ] 图谱命令、核心关系和源码复核范围。
- [ ] 主链路及异常/定时/异步分支的 Mermaid 图。
- [ ] 规则、状态、数据、配置、排序与例外表格。
- [ ] P0/P1 测试矩阵：正常、边界、组合、错误、回滚、并发/幂等（适用时）、外部桩和观察点。
- [ ] 待确认项与每个关键事实的可定位来源。

## 输出

按顺序输出：范围与证据边界；模块定义与关系图；实体/状态；主流程；规则表；排序/决策表；异常和运营分支；测试范围/用例矩阵；待确认；代码追溯；验证记录。

## 质量要求

- 业务术语优先，代码名只作为追溯证据；提供表格和 Mermaid。
- 不把静态分析称作真实发送、结算、数据库或生产验证。
- 不输出或持久化密钥；没有授权 LLM 时照常使用结构图谱和源码复核。
- 文档完成后校验引用有效、图表/章节完整、无密钥和无 Markdown 空白错误。
